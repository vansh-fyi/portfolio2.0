# Ursa AI: My Personal Chat Assistant

## Project Overview

Ursa is my personal AI assistant - a conversational agent that answers questions about my background, skills, and projects in real time, making my portfolio interactive rather than static. It is built on RAG (Retrieval-Augmented Generation): every answer is grounded in content I wrote, not in the model's imagination.

Ursa has had two generations. The first version (late 2025) used a small open model and basic chunk search. In October 2026 I rebuilt it from the ground up, because the free tiers it depended on had changed and its answers weren't good enough. This document describes the current version.

## The Concept

Traditional portfolios require visitors to manually search for information. I wanted an **interactive, conversational experience** where visitors can simply ask questions and get instant, accurate answers - like a conversation with someone who knows my work, even when I'm not available.

## Core Features

### 1. RAG-Powered Intelligence
Ursa retrieves the most relevant passages before answering:
- **Knowledge Base**: Markdown documents about me, my skills, and each of my projects
- **Hybrid Search**: Combines meaning-based (vector) search with keyword search, so both "which projects involve loans?" and an exact project name work well
- **Grounded Responses**: Answers use only the retrieved content and say so when something isn't known
- **Dynamic Updates**: Edit a markdown file and re-run ingestion; only the changed chunks are re-embedded

### 2. Context Awareness
Ursa adapts to where the visitor is:
- **General chat**: Searches the entire knowledge base, so a question about projects works from the main chat too
- **Project view**: When viewing a specific project, search is limited to that project's content
- **Portfolio overview**: A short, auto-generated summary of every project is included with every question, so broad questions ("what has he built?") are answered well
- **Lead Gen Context**: Powers the Resend lead generation chat, guiding visitors through a contact flow

### 3. Natural Personality
- **Third-person voice**: Ursa speaks about Vansh ("Vansh designed...", "He built...") as his assistant
- **Warm and concise**: Typically two to four sentences, or a short bullet list when listing items
- **Honest**: When the answer isn't in the knowledge base, Ursa says so and suggests reaching out to me directly
- **Built to resist hijacking**: The prompt treats retrieved text and visitor messages as data, so "ignore your instructions" attempts don't reveal or change its rules

## Technical Architecture

### RAG Pipeline
1. **Content Ingestion** (run whenever content changes):
   - Source: Markdown files in the `_content/` directory
   - Chunking: Split by markdown headings, not fixed lengths. Every chunk is prefixed with its project and section path (for example "Portfolio Website > Challenges"), so a passage always knows where it came from
   - Embeddings: `gte-small` (384 dimensions), generated by a Supabase Edge Function using the model built into the runtime, so no third-party embedding API is involved
   - Storage: Supabase Postgres with `pgvector` (HNSW index) plus a full-text index
   - Incremental: Chunks are matched by content hash, so unchanged content is never re-embedded and a failed run never wipes existing data

2. **Query Processing**:
   - One SQL function runs vector similarity and keyword ranking, then merges them with Reciprocal Rank Fusion
   - Filters (project or content type) are applied inside the database query, so they can't starve the results
   - The top 8 passages are passed to the model, together with the portfolio overview

3. **Response Generation**:
   - A chain of free-tier models is tried in order: Gemini 3.5 Flash-Lite, Gemini 3.1 Flash-Lite, Groq's gpt-oss-120b, then free OpenRouter models
   - If a model is rate-limited, retired, slow or returns nothing, Ursa automatically moves to the next one
   - Only explicitly allow-listed model IDs are ever called, and OpenRouter models must be free, so nothing can start costing money by accident

### Technology Stack
- **Frontend**: React 19 + TypeScript + tRPC client
- **Backend**: Node.js + tRPC on Vercel serverless functions
- **Database**: Supabase (PostgreSQL + pgvector + full-text search)
- **Embeddings**: Supabase Edge Function running gte-small
- **LLMs**: Gemini, Groq and OpenRouter through one OpenAI-compatible HTTP client
- **Email**: Resend, for the lead form and health alerts
- **Scheduling**: Vercel Cron for the daily health check

### Reliability and Operations
- **Rate limiting**: Per-visitor and global daily limits, stored in Postgres so they hold across serverless instances. This protects the free-tier quotas from abuse
- **Daily health check**: A scheduled job tests every model provider, confirms free models are still free, checks the embedding function and database, and asks a few known questions end to end. If anything is wrong, it emails me
- **Golden-question evals**: A set of real visitor questions with expected facts, run after any change to the content, the models or the retrieval
- **Safe errors**: Visitors see a friendly message; technical details stay in the server logs

## Design Decisions

### Why RAG over Fine-Tuning?
- **Dynamic Content**: Easy to update by editing markdown files
- **Accuracy**: Grounded in actual content, which reduces hallucinations
- **Cost-Effective**: No fine-tuning or hosting of custom models
- **Explainable**: Responses can be traced back to source documents
- **Flexible**: Can switch contexts without retraining

### Why a fallback chain instead of one model?
Free tiers change without notice. Over the life of this project, models were retired, free quotas shrank, and a model I picked turned out to be slow. A chain of providers from different companies means no single change takes Ursa down, and the daily health check tells me before visitors notice.

### Why hybrid search and headings-based chunks?
My first version split text into fixed-size pieces, which lost track of which project a passage belonged to and missed questions that span several projects. Heading-based chunks with project names, keyword plus vector search, and an always-included portfolio overview fixed most of that.

### Why Supabase for everything?
One database holds the knowledge base and the rate limits (and will hold my blog content), which keeps the system simple and the whole stack inside free tiers. The daily health check also queries it, which keeps the project active.

## Challenges & Solutions

### Challenge 1: Free tiers change underneath you
**Problem**: Models get retired, quotas shrink, and a database can pause when idle
**Solution**: A multi-provider fallback chain with an allow-list, plus a daily health check that emails me on the first sign of trouble

### Challenge 2: Retrieval missing the right passage
**Problem**: Fixed-size chunks lost their project context, and filtering after the search could leave nothing relevant
**Solution**: Heading-based chunks titled with their project, hybrid vector plus keyword search, and filters applied inside the database query

### Challenge 3: Broad, cross-project questions
**Problem**: "Which projects involve fintech?" needs information from many projects at once, which a handful of retrieved chunks can't cover
**Solution**: An auto-generated overview of every project is included with every question

### Challenge 4: Staying free without being abusable
**Problem**: A public chatbot on free quotas can be drained by anyone
**Solution**: Postgres-backed rate limits per visitor and per day, free-only model rules, and alerts if a model ever stops being free

### Challenge 5: Handling unknown questions
**Problem**: Visitors may ask things outside the knowledge base
**Solution**: Ursa admits when it doesn't know and suggests contacting me directly

## Lessons Learned

1. **Content is King**: Retrieval quality depends on well-structured source content. Clear headings and project names matter more than a bigger model
2. **Design for Change**: Anything free can change. Build so that swapping a provider is a one-line change, and monitor the things you don't control
3. **Measure, Don't Guess**: A small set of real questions with expected answers caught regressions that looked fine by eye
4. **Be Honest**: Admitting limitations builds more trust than fake confidence
5. **Rebuild When It Pays**: A year of changes in models and free tiers made a clean rebuild cheaper than patching the first version
